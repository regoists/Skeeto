# Skeeto project rules

Always use Simplified Chinese. This file maintains cross-task red lines and lookup entry points. The current user request decides goals and authorization scope; source code, real call chains, and matching live measurements decide behavior. Old comments, plans, handoffs, and reference material do not by themselves authorize action.

## Execution boundaries

- Keep all uncommitted, untracked, and machine-ignored files; if ownership is unclear, keep them. Without authorization, do not clean, roll back, stash, or commit, and do not casually change unrelated code or historical docs.
- Review, Q&A, and research are read-only by default. When a fix or delivery is already authorized, complete the necessary caller, data, test, and documentation changes; do not re-confirm the same authorization. Ask only when critical information is missing or the work would exceed authorization, and keep doing independent work that is already allowed.
- Before changing code, confirm entry points, callers, thread/frequency, re-entrancy, ownership, and how enable/disable, map change, disconnect, and exit invalidate state. After checking, leaving code unchanged is allowed; do not force a diff for its own sake. Authorized design fixes should be completed directly; out-of-scope refactors need separate explanation.
- Follow the task routing below to read the matching guides. Content already read in the same turn and unchanged may be reused. For cross-domain work, read the matching parts; do not mechanically read unrelated topics, re-run validation that still applies to the final content, or start unrelated tools.

## Top red lines

- **Minimal sufficient defense; ban meaningless defensive programming.** Every check, `__try`, fallback, and compatibility path must correspond to a real boundary or supported contract. Conditions already guaranteed by an upper layer within the same valid lifetime must not be re-checked lower down. Guarantees must not be reused across callbacks, async work, or invalidation edges. Hook/interfaces, entity entry and generation, external input, cross-thread use, and invalidated objects still need necessary protection.
- **Prefer performance, stability, and simplicity.** Optimize against net gain over the full same-condition target interval, including init, checks, maintenance, copy, sync, IO, and cleanup; local microbenchmarks do not prove full load-time speedups. Mechanisms without stable net gain may only be marked experimental and must not keep stacking.
- **Bound high-frequency work.** Paint, FSN, CreateMove, and Event/recv must not unbounded-scan, block, repeat expensive queries, or log without budget. Source/L4D2 interfaces not proven thread-safe may be used only on already-confirmed-safe game/Paint threads; Event/recv may only record light state or write bounded queues; workers must not call engine, cvar, command, or entity interfaces.
- **Hot paths must not call `VirtualQuery` directly.** Game memory reads go through `src/skeeto/core/skeeto_memread.h`; cold-path page queries and exception registration are in the performance guide. Readable/executable does not prove object identity, liveness, or ABI.
- **Do not pile on mechanisms.** When a symptom comes from an existing design, first state the root cause and the lasting fix direction, then correct within authorization; for performance symptoms, measure first. Shared helpers must not hide syscalls, locks, allocation, or IO; cost is judged by frequency and growth state. For abnormal faults, reuse existing counters or rate-limited logs; normal shutdown, no-target, and similar branches do not require new diagnostics. Temporary diagnostics are cleaned after the fix and targeted verification; long-lived diagnostics need ongoing purpose.
- **Small-update hardening keeps current behavior.** Prefer fixing clear boundaries such as continuing without a required dependency or writing after write-permission failure; separately verify that the normal path stays equivalent and that failure stops dangerous calls/writes, and check partial writes, callers, and cleanup. Do not rewrite normal slots, layouts, coexisting Hook chains, or add global version locks based on assumed future ABI changes; new integrations must not probe unknown slots by trial calls to guess ABI.
- **New active features default off.** After new HUD, effects, sounds, and active enhancements are off, they must produce no dedicated visible, audio, engine impact, or high-frequency work; bounded edge cleanup still required by other consumers, and shared work those consumers still need, are allowed. Reuse existing `Wanted()`. Internal parameter defaults, internal helpers, and fixes to existing features follow their own responsibilities.
- **Exit must be stable.** Feature off, map change/disconnect, explicit unload, and process termination are handled separately. Normal restore happens on a safe thread while the target is still valid; after a worker exits because the module unloaded or a window was destroyed, do not restore game RecvProp/vtable. Process termination must not attempt late restores.
- **Prefer the new version; do not deliberately compatibility-shim old versions.** Across the project, aim for the new implementation to be correct, effective, reliable, and simple. Compatibility with old versions, old configs, or historical behavior is not a default requirement; do not deliberately add migration, aliases, speculative merges, extra fallbacks, or keep discarded implementations for compatibility. When compatibility would add complexity, maintenance cost, or hurt the new design, adopt the clear new implementation, state necessary incompatibilities, and keep the user's original files—do not automatically delete or overwrite old data. Normal features that should work now, and interfaces/install/update contracts the current task explicitly requires retaining, must still work; do not use "incompatible with old versions" to hide regressions. This principle applies to every module.
- **Put only useful files in the game root.** Startup depends on root `skeeto.dll` and `bin/wininet.dll`; install/update deploy only those two DLLs and the menu-opened root `Skeeto_更新日志.txt`. Package version files, workshop markers, old-pump scripts, and the maintenance engine stay inside the package/staging area and are not spilled into the game root. Do not add install receipts, readme folders, settings backups, or other purposeless files; the fixed cleanup list, user settings/assets, and other-platform protection are in the release guide. Saving settings only deletes the historical `skeeto_setting.ini.before-key-cleanup.bak` and does not create new backups.
- **Do not leave one-off artifacts in the workspace.** `tools/` holds tracked scripts and machine-local tools still read by build or tests: Ghidra and REA under `tools/local/reverse/`, migration packages under `tools/local/bootstrap/`, and `tools/local/analysis/viewmodel/` plus `tools/local/feedback-sources/`. Do not install IDA or Dependencies. Tests use the system temp directory and delete it when finished; installer copies, decompile dumps, and evidence directories do not stay under `tools/local`. Material worth keeping goes in `archive/`.

## Compatibility and product conventions

- Building a desktop package, Git integration, external distribution, and workshop upload are different states. The real user compatibility baseline only recognizes versions already distributed to players; developer machine deploys and preview trials do not count. Unpublished intermediate formats, settings keys, and behavior are changed directly to the target shape without migration, aliases, or cleanup lists. Already-published user data must still be protected; state necessary incompatibilities proactively; do not casually delete unrelated historical compatibility code.
- Changelogs cover user-visible changes from the previous really released version to the pending version; do not record trial-and-error fixes from unpublished iteration. Version, artifact hashes, and distribution state follow root `VERSION.txt` and `docs/agent-guides/release-and-updates.md`.
- For numbered menus with a settings subpage, the parent page keeps only one "【进入设置】" entry; toggles live on the subpage; drawing and input must stay in sync. Custom main menu, ESC menu, and in-game HUD are independent modules and must not share config or input gating.
- English localization uses `skeeto_ui_text.h` and `skeeto_ui_en.inc`. Explanatory body text is provided in Chinese and English; product names, native terms, and short labels are kept by meaning; do not change Chinese default behavior, and do not introduce hot-path allocation, IO, or repeated resource loads. Game text uses verified font glyphs; unconfirmed symbols prefer ASCII; `±` is known to render as `?`.

## Source, build, and install entry points

- Skeeto is an L4D2 client enhancement DLL. The 2.0 Steam direct-start entry is `bin/wininet.dll`, which forwards system x86 WinINet and loads root `skeeto.dll` before the core is running; the core rejects a second physical image in `DllMain`.
- The source of truth for source code is `src/skeeto/`; the source of truth for version is root `VERSION.txt`; do not modify the build mirror `packages/Skeeto/source/`. File responsibilities and search entry points are maintained only in the module map in the performance guide; read implementation detail via map links as needed. Features usually target remote servers; local-server-only capabilities must be clearly marked.
- **After project code changes, you must run `cmd /c src\skeeto\build.bat`**, wait for the MSVC x86 build and ordinary deploy final exit result, and check whether the game root was updated. Safely solvable deploy problems should be cleared and the build re-run; if unfinished, report honestly. Rules, docs, or Skill-description-only changes do not need build/deploy.
- Local development deploy may exit/end the target L4D2 under existing authorization, preferring a normal exit, and if necessary ending only a verified-path `left4dead2.exe`, while keeping settings and mods. When the user asks to stop game operations or to test themselves, prefer that; deploy authorization does not override that stop request and does not automatically authorize a new round of live acceptance.
- Ordinary builds update `runtime/dll/skeeto.dll`, `runtime/bootstrap/wininet.dll`, the development deploy, and `packages/Skeeto-dev/`; they do not update the desktop formal package or `release/`; they do not generate a same-content `necola.dll`. The user copies `packages/Skeeto-dev/` to desktop `Skeeto_<version>/` themselves when they want a formal installer; a release or version bump updates `packages/Skeeto-dev/` only and does not create the desktop pack; do not use a previous desktop pack as the next version's base. Game root is resolved from `SKEETO_GAME_ROOT`, ignored `src/skeeto/build.local.bat`, or script defaults; shared files must not contain machine absolute paths.
- Maintenance scripts are written for Windows PowerShell 5.1 and launched with `powershell.exe`; do not rewrite them to PowerShell 7 just to unify terminal versions.
- External research samples go in ignored `reference/`; `vendor/` only holds third-party dependencies that actually participate in build or runtime; do not create the directory empty. The core workshop ID is `3787239937`; the preset asset pack is `3782512354`.
