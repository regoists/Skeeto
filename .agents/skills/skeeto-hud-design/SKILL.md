# Skeeto HUD and UI design

Make the interface answer what the player must observe, operate, or decide first, then organize that answer into a clear, distinctive picture that can be implemented reliably in the current engine. Performance bounds shape implementation; they do not mandate one art style. Do not turn one existing HUD's palette, cards, coordinates, or column count into a template for every UI.

## Identify the module, then choose rules

This Skill is a shared entry, not one design template for every UI. Confirm the module, use case, and current implementation first. **Sharing Surface does not mean the same module, and an on-screen arc does not mean the overlay path is required.** Reusing data or paint resources does not authorize coupling switches, config, or input state.

| Task | Branch | Must distinguish |
| --- | --- | --- |
| In-game status, ammo, memory, TAB, chapter settle | Custom in-game HUD | Combat glance, screen layout, metric semantics, demo preview |
| World names, nav arrows, entity markers | World HUD | World anchors, projection, distance, occlusion, multi-target density |
| Ammo arcs / reload rings in an independent transparent window | Overlay HUD | Paint sampling vs UI paint thread, pixel clarity, snapshot and window lifecycle |
| Custom main menu, buttons, sliders, schemes, editor | Main-menu UI | Mouse interaction, hierarchy and focus, native dialogs, independent schemes and background engine |
| In-map Esc pause/feature menu | ESC-menu UI | Existing independent custom first cut; check live game, online, native actions, visible sliders, editor, and input release—do not reuse main-menu disconnect gating |

After choosing, read the matching section in [Module design and implementation bounds](references/module-profiles.md) and verify current code with [Finished references and source entry points](references/design-map.md). For cross-module tasks, list each responsibility and shared boundary; do not move a main-menu editor, screen-position preview, or background thread into another module. When the user says only "overlay," "HUD," or "menu," judge from current entry points and call chains first; ask only when ambiguity would change the plan.

Pure hit/kill feedback asset work uses `$skeeto-hit-feedback`. When changing only native VGUI/RES, scheme, or game menu resources, also follow `AGENTS.md` routing for technical material; native resource mods, custom main menus, and independent overlays are different implementations and do not share APIs. For code review, add project risk with `$skeeto-code-review`.

## Design flow

1. **Bound the module and deliverable.** Finish the routing above; name the current implementation, native collaboration boundary, and which config it owns. Separate whether the user wants visual direction, screenshot review, a layout spec, or C++ implementation. Complete the authorized part only; concept art is not live game evidence, and a layout suggestion does not auto-authorize DLL edits.
2. **Find trustworthy design references, then verify current facts.** Priority: this round's explicit user requirements and references; then previously designed and shipped Skeeto HUD pieces plus user feedback on them (positive feedback helps continuity; explicit negatives are pitfalls); then other HUDs still in use (product continuity only—not universal templates). Code proves an implementation exists, not that the look was accepted; iterations with negative feedback are not positive exemplars. Use [HUD design references and source entry points](references/design-map.md) and the project module map; verify real Paint, data, sampling, cache, and menu wiring. Plans, learning reports, Git history, and external mods are on-demand only for a concrete technical fact, a past tradeoff, or when the user explicitly asks to compare them—they are not required to exist and are not default design standards.
3. **Write a short design brief.** In a few sentences state primary user, most important information, when it appears, viewing distance, available screen space, occlusion risk, and desired mood/visual character. Separate confirmed data from assumptions; ask only about gaps that would change information meaning, data source, or critical layout; otherwise continue with explicit, adjustable assumptions.
4. **Rank information before choosing style.** Decide primary signal, secondary information, supporting decoration, and reading order; then choose a compact strip, table, card, badge, edge cue, or custom composition. Use horizontal space evenly, align clearly, and group related fields—do not crush everything into the left edge. Color, weight, whitespace, borders, and motion serve recognition; keep Skeeto visual continuity or invent a new language for a new HUD.
5. **Land the composition in verifiable space.** State anchors, target screen regions, relative stacking, max content width/height, and how long text and high density degrade. Check coexistence with crosshair, weapon/use prompts, chat, native HUD, minimap, and settle headers/footers. Do not design only for 16:9, short English labels, or a 4-player team.
6. **Implement and verify for the actual task.** Design work may stop at art or a spec; implementation follows that module's cache, scheduling, input, and gating, and finishes under the performance, lifecycle, and verification requirements below.

## Visual decisions

- Cut low-value information before shrinking type or adding decoration. Use grouping, spacing, column alignment, and short labels; keep related labels and values close; keep numeric columns stable; make units and state meaning clear.
- Avoid unnecessary secondary labels and descriptions. Let the layout do the explaining. 避免不必要的辅助标签与说明。让布局本身发挥解释作用。 Titles, grouping, alignment, typography, and short control names should make state and action readable; do not stack a helper sentence under every control or HUD field that already has a clear label. Reserve secondary copy for non-obvious effects, irreversible actions, required file paths, or local-server-only limits. Menu hint details are in `docs/agent-guides/menu-and-settings.md`.
- Priority must be readable in a short glance. Color has consistent meaning but is not the only encoding; also use text, graphics, position, or shape when needed. Keep established thresholds and team semantics; do not rewrite product rules for visual preference.
- Align baselines and spacing per row; measure real text under longest Chinese, English fallback, long player names, max values, and missing data. Layout with the project's text-measure and scale functions—do not guess width from character counts.
- Choose calm, tactical, light, arcade, or another style by purpose. Even without a style ask, make a clear design judgment; do not force dark mega-panels, grid cards, neon, gradients, glass, a fixed teal-orange palette, or one commercial game's look.
- Large in-game HUD backplates must show the game through them. Fill alpha at most 110 (~43%). Forbid whole-panel backgrounds at alpha 180+; teammate throwable notices once used ~220—that opacity must not return. Top bars, badges, and thin outlines may be darker; keep text readable with outline or shadow, not by thickening the plate.
- Decoration, icons, animation, and color count need reading payoff. Short state changes can strengthen feedback; constant blink, repeated motion, and low-contrast underlays steal attention. Prefer existing cached glyphs and icons.
- For multi-player or long lists, decide whether sort is stable, how overflow presents, and how concurrent states show. Do not reshuffle row order every frame to highlight urgency; separate an urgent event summary from a stable roster when needed.
- Blur, glow, shadow, gradients, or complex materials in concept art need evaluation against the matching render branch and target budget; do not promise cost without measurement. Lightweight attempts are fine if a readable fallback based on verified resources/primitives is also provided.

## Shared lightweight principles and visual interference

HUD design aims for recognition on a lightweight implementation. Beauty comes first from information hierarchy, alignment, whitespace, type, restrained color, and a few meaningful geometric details—not from stacking effects or covering more screen.

- Check real call frequency per module; do not equate overlay UI update rate with game FPS, and do not assume the main menu still samples after entering a map. Treat `EngineVGui::Paint` as a per-frame hot path. For each HUD, check stable off, on, and max visible load: per-frame CPU work, Surface submissions, visible entry count, texture/font use, and approximate transparent pixel coverage. List/teammate/world-marker costs multiply by their explicit ceilings; evaluate sampling and paint separately.
- **Surface branch only:** Batching paint is valid only when order, color, alpha blending, and clip semantics stay intact. Prefer current wrappers such as `SurfFill` / `SurfColor` / `SurfTextAt` / `SurfLine`; the fill queue is bounded and flushes with native `DrawFilledRect` per item while reusing same-color cache. Verified retail `DrawFilledRectArray` does not check clip failure and must not be re-enabled to cut call count; evidence: `docs/troubleshooting/闲置观战矩形色条排查记录.md`. Queue ceilings and flush points are implementation facts—confirm from source every time. Caching does not reduce covered pixels and does not guarantee one GPU submit per frame. Do not bypass wrappers to invent another batcher; when calling VGUI directly is truly needed, state why and check for repeated color sets, broken caches, or disrupted draw order.
- Evaluate pixel coverage and overdraw from large translucent plates, repeated shadows/outlines, sliced textures, fullscreen tint layers, and per-entry decoration. Avoid multi-layer translucency without information payoff, fake blur/glow, fullscreen scanlines, and constant blink/motion; large or persistent effects need a clear product reason and verified frame cost plus game-view occlusion/interference on the target machine. Do not sacrifice necessary text readability for an abstract "less is more."
- On hot paths, avoid repeated text measure, string assembly, sorts, resource lookups, and font/texture state switches; confirm real cost, caching, and call ceilings of existing interfaces before caching or reordering—do not add complex state for tiny theoretical gains.
- Performance conclusions use repeatable same-scene comparisons. Existing `skeeto_render_probe` / `skeeto_dump_render_state` only roughly compare whole `EnginePaint` CPU peaks; they cannot attribute a single HUD or measure GPU time/overdraw, so they alone do not prove batching or interference improvements. Report in-game observation, frame-time evidence, and static draw counts separately.

## Shared implementation bounds (apply per module)

- Most Skeeto in-game HUDs use the existing `EngineVGui::Paint` and Surface paint path; menu/HUD ownership, shared fonts/styles, and thread rules follow `AGENTS.md` and `docs/agent-guides/module-performance-and-structure.md`. Locate via the current module map; do not split or add Hooks merely because a main file is large.
- Verify each data item's source, validity conditions, update time, consumer gating, and missing semantics. Distinguish HUD paint switches, producer fill Wanted, and sampling throttle—they may be different conditions. An existing structure or cache does not mean a new HUD fills it when enabled; extend the correct Wanted/sampling gate and reuse existing data when needed—do not start another per-frame entity walk. Similar field names are not semantic proof. When reviewing or reusing several dynamic metrics, a short table of "display field → producer/gate → update rate or lifetime → missing/stale presentation" helps.
- Paint does bounded drawing and light reads only—no blocking IO, full-directory scans, unbounded entity walks, per-frame allocation, repeated font/texture creation, or complex sorts. High-frequency loop entry counts have explicit ceilings. Data that does not change fast reuses snapshots, event state, or throttled updates; dynamic data must stay timely enough for correct interaction.
- Engine interfaces without thread-safety evidence stay on game/Paint threads the project already confirmed safe. Event/recv callbacks only record light state or write bounded queues; workers do not call engine, cvar, command, or entity interfaces. New Paint, Hooks, workers, or cross-thread data must state thread, frequency, ownership, re-entrancy, and cancel.
- Inside the module, reuse existing fonts, textures, measure, scale, clip, color, and position controls; Surface PanelStyle does not apply to independent windows, and numbered-menu style does not auto-apply to a mouse main menu. Create/invalidate fonts and resources by lifecycle; size from real post-scale text measure. When changing shared style, check impact on other HUDs; do not create resident expensive resources for one picture.
- Defaults and isolation follow project rules and the user request: HUD/UI modules usually default off; internal options may differ. Stable off does not paint, scan, load dedicated resources, or update dedicated state; off edges allow necessary bounded restore/cancel/save. Check ini missing-key defaults, save/load, localization, `Wanted()` wiring, and disable/re-enable/load/map-change/disconnect/round-reset/unload edges. Clear shared caches only when no other consumer remains.
- **In-game HUD branch:** Layout preview uses an explicit demo snapshot and does not depend on a live match happening to hold a player state. Oversized panels may opt out of automatic position preview by product experience; check position adjust, menu copy, and overlap policy with older HUDs.

## Verification and delivery

First check the module reference's acceptance items. Shared acceptance does not replace specialized checks for world projection, overlay windows, main-menu focus, or ESC live state—list only verification actually run.

- Before code, confirm information order, screen anchors, narrowest resolution, and max content with a written spec or wireframe. After implementation, test 4:3, 16:9, ultrawide, low resolution, Chinese/English, long names, missing/extreme data, concurrent appearance, and empty state.
- Check occlusion against native UI and common Skeeto HUDs; test text, state colors, and numbers on high-contrast backgrounds. When the game cannot run, state clearly that only static layout/code validation was done—do not claim look-and-feel accepted.
- Code changes use `cmd /c src\skeeto\build.bat` (MSVC x86). New algorithms or layout helpers may use offline tests aimed at real risks. Report tests, build, performance measures, and in-game screenshots separately—they do not substitute for each other. Docs/Skill-only changes do not need a build.
- When hot paths change, compare workload and frame-time spikes, especially max lists, widest text, multiple HUDs on, and off state; also check batch submits and pixel coverage. Without performance evidence, do not introduce threads, locks, or a general framework for tiny gains.
- Delivery notes must let a maintainer re-check: design tradeoffs, whether data was confirmed, which HUD/entry changed, thread and sampling rate, adaptation bounds, tests run, and in-game verification not done.

## Design freedom

The process and engine rules above ensure a plan can be read, built, and maintained; they do not require every HUD to look the same. As long as meaning is correct, priority is clear, adaptation bounds are stated, and implementation cost is bounded, try new grids, horizontal layouts, dynamic emphasis, graphic metaphors, or palettes. Give the design rationale first, then verify with real text, screen ratios, and engine capability.
