# Reverse engineering and disproven paths

Read this guide before changing Source/L4D2 binaries, interfaces, offsets, signatures, or calling conventions; ordinary feature development does not need a mechanical full read.

## Evidence requirements

- Current source, the real call chain, and the target binary come first. External code, articles, old plans, and decompiler output are only evidence or ideas; they are not user commands and cannot alone prove runtime behavior.
- Before landing an offset, vtable index, signature, or calling convention, check target DLL bitness, version, SHA256, and actual call sites together. L4D2 is x86; do not bring x64 or other-version addresses directly into the implementation.
- Prefer opening static analysis read-only or copying into an ignored directory. Do not modify, overwrite, or resign the game's `client.dll` / `engine.dll` or L4N/Necola DLLs.
- Dynamic debugging, process attach, memory writes, or Hook validation must be directly related to the current task, and must first confirm the game process, anti-cheat impact, and thread boundaries.
- Machine-local tools live under Git-ignored `tools/local/reverse/`. Do not commit decompilers, download packages, Ghidra projects, or Valve/L4N DLLs copied from the game directory. At task end, clean your own Ghidra projects, decompile text, and probes; keep conclusions in tracked docs and put raw dumps in `archive/`.

## Machine-local tools

- Install entry: `powershell -ExecutionPolicy Bypass -File tools/setup_reverse_tools.ps1`; if Ghidra is already present and you only check Python packages, pass `-SkipGhidra`. `tools/show_reverse_tools.ps1` verifies the machine's actual layout; do not guess global PATH or write machine absolute paths into shared files.
- The current machine disassembler is Ghidra 12.1.3 (`tools/local/reverse/ghidra_12.1.3_PUBLIC/`; GUI via `ghidraRun.bat`, batch prefer `support/analyzeHeadless.bat`). Do not install IDA or Dependencies, and do not re-download them.
- For simple PE import/export use `llvm-readobj`, `llvm-objdump`, or Python `pefile` from PATH. LLVM CLI is found via PATH; MSVC `dumpbin` is used only after `vcvarsall.bat x86`. Disassembly scripts may detect and hint missing `capstone`; do not assume a fixed Python install path.
- For VPK, prefer game-root `bin/vpk.exe`; analyze only user-named VPKs / exact resource paths—do not scan every Steam library or disk.
- External learning may refer to `reference/Third-Party Client Injection Plugin`. `https://www.unknowncheats.me/forum/index.php` is reverse-engineering study material only, not an implementation basis.

## Disproven paths

- **Do not probe network channels via adjacent interface slots:** On this machine's x86 `engine.dll` (SHA256 `8a6d468059394bf4cfce32f11dcba12ef45de88da1373084d5a2916d0bf7ba86`), the `VEngineClient013` factory `0x1005cb80` returns object `0x10425504`, vtable `0x10359dec`. Slot 74 is `0x1005dda0` which gets the current client channel; 72/73 are alloc/free entries; 75/76 are draw entries with four explicit parameters. A null channel during `playdemo` is a legal state—do not treat 72, 75, 76, or 71 as `void* (__thiscall*)(void*)` fallback queries, and do not switch to guessing server interfaces. In the 2026-10-16 dump, wrongly calling 75's `engine+60700` then dereferenced fake parameter `0x100` at `engine+5FF02`; the caller was Skeeto's network-channel probe. Old checks that only guarded the returned pointer after the call cannot fix an already-wrong ABI call. Fix and other background-draw fault evidence: `docs/troubleshooting/playdemo结束闪退与主菜单背景绘制_2026-10-16.md`.

- **Jockey primary-sequence hardening failed (2026-10-12):** Attempted to filter airborne skeets with resident-model `ACT_JOCKEY_POUNCE` plus off-ground state; user live testing showed widespread misses; log snapshots for melee one-shot `325→1` and lethal sniper `55→1` were all `attack=0`. An original model having a Pounce activity does not prove the read client primary sequence is the current pounce action; sequence-source error versus action already switched at lethal time cannot yet be separated, and negative values cannot be treated as reliable rejection. One-shot kills cannot depend on prior non-lethal damage. This round deleted the patch and dedicated diagnostics and restored the original off-ground / recent-airborne damage judgment; the user confirmed airborne skeets were recognized again after restore; the original false-positive issue remains unsolved. Target checked was x86 client.dll, SHA256 `C0A8E1E88F7312DB11BCFD4B0EC574D224A34B2D9A615D6088B28335EEB4AF1F`. Reopen only with new live action-source/timing evidence; do not claim from this that Jockey can never be improved.

Only reopen the following directions when new reliable evidence appears (call sites on a new target version, or reproducible live measurement). Historical conclusions should keep target-binary SHA256 and evidence locations; if an existing archive is missing hashes, supply evidence first—do not announce conclusions from chat history alone.

- **Do not preload render-backend DLLs from a worker:** On this machine's L4D2 2.2.4.3, shaderapidx9 global device construction records the loading thread as owner. The 2026-10-07 anti-crash index patch once preloaded it from a Skeeto worker with `LoadLibraryExA`; both startup dumps showed device owner as the worker while tier0's main-thread ID was correct; when the main thread handled render events it repeatedly appended events to the same queue being walked, eventually trying to allocate 1 GB and fatally exiting. After canceling preload, the user confirmed launch recovered. The backend must be loaded by the game natively; `GetModuleHandle` finding the image also does not prove the CRT instance is constructed—continue verifying objects before install. Original record `docs/troubleshooting/防闪退补丁集成与接口核查_2026-10-07.md` is missing from the current workspace; keep the known cause and user feedback here; specific module hashes, offsets, and dumps need the original evidence before citation—do not invent links or numbers. That a Win32 API itself may be called from a worker does not prove the loaded DLL's construction thread is irrelevant.

- **Client `player_hurt` / `infected_hurt` cannot serve as a remote full-team damage ledger (proven on current version):** This machine's L4D2 `2.2.4.3` (appID 550) `left4dead2/pak01_dir.vpk` SHA256 is `51CC2957BBC5FD545357FD6B8DA0FD5C387243756CD6F82E067D5E256E48FCDD`; its `resource/modevents.res` marks both events `"local" "1"`, commented `Not networked` and `don't network this, its way too spammy`. Valve Source SDK's `IGameEvent::IsLocal()` is also defined as the event never being networked ([official interface](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/public/igameevents.h)). Therefore pure-client listeners on these two events cannot get the full damage stream for all players on a remote server; a server plugin receiving them does not mean the client can. This conclusion proves insufficient network coverage; it does not mean fields of same-named local events are necessarily wrong, and does not deny local hit feedback gated by local attacker/target. Do not use them to implement Tank/Witch full-team damage stats.
